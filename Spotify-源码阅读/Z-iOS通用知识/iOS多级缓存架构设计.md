# iOS多级缓存架构设计

> 关联源码笔记：[[SPMusicRepository]]

## 核心概念

刷题手写的 LRU（哈希表 + 双向链表）只是一个**内存数据结构**；而在真实客户端工程中，为了平衡**读取速度、存储容量、断电留存与流量消耗**，通常会构建 **L1 / L2 / L3 多级缓存体系**（原理与 CPU 的 L1/L2 Cache → 内存 → 硬盘完全一致）：

| 层级 | 名称 | 存储介质 | 存什么 | 耗时量级 | 容量规模 | 生命周期 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **L1** | **内存缓存（热缓存）** | 手机运行内存 (RAM) | 已解析/已解码的对象（Model、`UIImage`、`AVURLAsset`） | 纳秒~微秒（0 IO） | 小（几 MB ~ 几十 MB） | 杀进程即失，受系统内存警告制约 |
| **L2** | **磁盘缓存（温缓存）** | 沙盒 `Library/Caches` | 原始文件或序列化字节（`.mp3`、图片文件、JSON/SQLite） | 毫秒级（需磁盘 IO + 反序列化） | 大（几百 MB ~ 数 GB） | 持久化留存，断网/冷启动可用 |
| **L3** | **远程源站（冷数据）** | 服务端 API / CDN | 权威源数据 | 百毫秒~秒级 | 无限 | 受网络环境、鉴权与签名时效限制 |

- **冷/热缓存的含义**：高频访问、驻留在最快介质（L1 内存）中随时可 0 开销读取的数据称为**热缓存（Hot Cache）**；低频访问、退居 L2 磁盘甚至尚未拉取的数据称为**温/冷数据**。
- **经典读取与回填链路**（以 `SDWebImage` / `YYCache` 为代表）：
  1. 查 **L1 内存** → 命中直接返回；
  2. 未命中查 **L2 磁盘** → 命中后反序列化/解码为对象，**回填写入 L1**（把温数据升为热数据），再返回；
  3. 仍未命中请求 **L3 网络** → 拿到数据后**写 L1 内存 + 异步落盘 L2**。
- **磁盘 LRU 的工程实现（索引与文件分离）**：
  - 磁盘文件不直接维护链表指针，而是**在内存中用一个轻量级 LRU 容器只存 `key -> 文件字节大小`**（内存体积仅几 KB），把 `allKeysInMRUOrder` 异步持久化到 `manifest.json`。
  - 当内存索引的总字节（`totalCost`）超过磁盘上限（如 200MB）触发淘汰回调时，再去后台串行队列删除对应的沙盒文件。

## 在本项目中的实际应用

- **源码位置**：
  - 基础容器：`Spotify/Core/Cache/SPLRUCache.h`
  - 纯 L1 元数据缓存：`Spotify/Data/Repository/SPMusicRepository.m:L18-L50`
  - L1 + L2 多级音频缓存：`Spotify/Player/Cache/SPAudioCacheManager.m:L24-L79`、`L276-L320`
- **实现方式**：
  1. **业务元数据（`SPMusicRepository`）只做 L1 内存缓存**：歌单、专辑、搜索结果体积小且实时变化，只用 6 个 `SPLRUCache` 驻留内存，杀进程重拉即可，省去磁盘迁移与脏数据管理成本。
  2. **音频流（`SPAudioCacheManager`）采用 L1 + L2 双级架构**：
     - **L1 内存热缓存**：`resolvedURLCache`（缓存 15 分钟有效期的播放直链）+ `assetCache`（预热最多 6 个 `AVURLAsset` 实例）。
     - **L2 磁盘缓存**：`Library/Caches/SPAudioCache/<safeKey>.mp3`（上限 40 首 / 200MB），通过 `diskIndexCache`（`SPLRUCache`）在内存中维护磁盘文件的体积与 LRU 淘汰顺序。
     - **流媒体特有的优先级**：播放时先看 **L2 本地是否有完整音频文件**（有则直接走 `file://` 零流量秒播并回填 L1 `assetCache`），没有再用 L1 预热的远程流边播边在后台静默下载落盘到 L2。
- **关键注意事项（工程级缓存必考的 4 个补丁）**：
  1. **双维度容量限制（`maxCount` + `maxCost`）**：大文件（音频/大图）不能只限条数，必须按字节数传入 `cost` 防止单文件撑爆内存或磁盘。
  2. **内存警告区分对待（`trimsOnMemoryWarning`）**：纯 L1 内存缓存收到系统内存警告时自动清理保命（默认 `YES`）；而用来记录磁盘文件索引的 `diskIndexCache` 必须设为 `NO`（`SPAudioCacheManager.m:L65`），否则一收内存警告就把磁盘账本丢了。
  3. **TTL 过期校验（Time-To-Live）**：LRU 只管“最近有没有用”，不管“有没有过期”。带防盗链签名的音频直链必须额外记录时间戳（15 分钟 TTL），过期强制失效。
  4. **缓存预热（Warm-up / Preload）**：首页拉回数据后顺手注入 `playlistCache`（`warmCachesFromHomeSections:`），以及播放当前曲目时后台 `preloadTracks:` 提前填充下一首的 L1/L2。

## 关键问题沉淀

- **Q: 为什么切换数据源时，元数据缓存全清，而音频缓存只调用 `clearMemoryCaches` 清 L1 却保留 L2 磁盘？**
  - L1 里存的是旧数据源会话下的内存对象和临时防盗链 URL，不清理会占内存或串源；而 L2 磁盘里存的是实打实下载好的 `.mp3` 文件（按曲目唯一 key 命名），保留下来后用户再切回原数据源听同一首歌时依然可以离线秒播，避免重复消耗流量下载。
